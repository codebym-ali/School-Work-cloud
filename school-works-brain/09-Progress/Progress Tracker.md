## ➕ Guardian optional at admission (2026-07-30)
Operator: *"to admit a student we need to fill this whole form — make the guardian optional."* A walk-in can now be seated before the guardian's details are collected.

- **The codebase was already tolerant — only three things forced it.** Traced every consumer first: SMS dispatch resolves `primaryGuardian` and **returns quietly when there is none** (all 4 types), fee **advance auto-application** bails on a missing `parentId`, the student detail screen already rendered *"None."*, reports never touch guardians, and `student_guardians` is a link table where **zero rows is already valid — no migration**. The one-primary partial unique is `WHERE is_primary = true`, so it is unaffected. Only `CreateStudentDto.guardian!`, `createStudentCore`'s unconditional `resolveParent`, and the form required it.
- **⚠️ The risk is silence, not breakage.** A guardian-less student receives **no absence, fee-receipt or result SMS — ever**, and nothing said so. Schools that make this optional without a safety net accumulate contactless minors and only discover it in an emergency. So the design rule was **optional to enter, never invisible**:
  - `GET /students` returns **`hasGuardian`** (a `_count`, not the guardian rows — presence shouldn't inflate the directory payload).
  - Directory rows carry a **`no guardian`** badge; a **⚠️ Missing guardian** chip filters to exactly those students (`?missingGuardian=true` → `guardians: { none: {} }`). That chase list is what stops "record it later" meaning "never".
  - The form states the consequence **before** submit, not after.
- **Half a guardian is still rejected.** The DTO keeps `@ValidateNested` under `@IsOptional`, and the form only omits the object when the section is **completely untouched** (`guardianTouched`) — so a partly-filled guardian 400s instead of being silently dropped. Omitting is a deliberate choice; a typo is not.
- **`POST /students/:id/guardians` opened to `ADMISSION_CONTROLLER`** (add only — edit/remove stay OWNER/CAMPUS). Without this, deferring is a dead end: the officer who admitted the student could not complete the record, only an owner could. Matrix row added.
- **`CreatedStudent.parentId` is now `string | null`** — callers already tolerated it; the direct-admission and admissions-admit paths still pass a guardian when the form supplies one.
- **Deliberately unchanged: CSV import still requires `guardianName`/`guardianPhone`.** A bulk file of 200 contactless students is the disaster case this feature's safety net exists to prevent, and an import is a reviewable, deliberate act unlike a walk-in. Flagged to the operator rather than changed unilaterally.
- **New spec** `guardian-optional.e2e-spec.ts` (4): admit with no guardian at all (asserts **0** links **and 0 ParentProfiles** — no placeholder parent invented), the flag + chase list are correct across a with/without pair, a half-filled guardian **400s**, and the admission officer can close the gap later with the late guardian becoming **primary** (otherwise SMS would still reach nobody).

## ➕ Student CNIC readable by an audited reveal + portal-login status on the profile (2026-07-30)
Operator asked for the CNIC on the student profile. It **could not simply be displayed** — only `cnic_hash` (an HMAC login factor) existed, and a digest cannot be reversed. Showing it required changing how it is stored, which reverses audit fix #5's write-only rule, so it was put to the operator as an explicit decision rather than assumed.

- **Decision (operator, 2026-07-30): store encrypted, reveal to admins.** New `students.cnic_enc` (migration `20260730120000`, AES-256-GCM, same `FieldEncryption` as guardian/teacher CNICs). `cnic_hash` **stays** — the two are not interchangeable: the hash answers *"does this match?"* at login, the ciphertext answers *"what is it?"* for board forms and certificates. A school genuinely needs the second; teacher CNICs never did, which is why that one remains write-only.
- **Reveal is its own audited endpoint, not a profile field.** `GET /students/:id/cnic` (OWNER/CAMPUS_ADMIN — deliberately **not** the admission officer, who captures it but has no reason to read it back) writes `STUDENT_CNIC_REVEALED`. Had the value ridden along with the profile load, every page view would decrypt and there would be nothing meaningful to audit. **The audit row records identity (name + GR), never the number** — a trail must not become a second copy of the secret.
- **`getOne` now strips both secret columns** and returns `hasCnic` / `cnicRevealable` / `portalLoginEnabled`. Three CNIC states, because **"never captured" and "captured but unreadable" are different facts**: a CNIC recorded before this migration still verifies a login but cannot be shown, and the UI says exactly that instead of implying it was lost. **No backfill is possible** — a digest cannot be reversed.
- **Portal-login status added** (operator's other pick): the profile now states whether the student can sign in and with which registration number. Previously invisible — there was no way to tell whether a login existed.
- **Gates:** api+worker build ✅ · web tsc ✅ · root lint ✅ · web lint ✅ · **full `pnpm test` 474 green** (unit 36 · integration 431 / 28 suites · isolation 7) · RLS coverage ✅ after `db:sql` (**again not automatic on migrate**).
